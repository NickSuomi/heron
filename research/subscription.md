# Heron issue 8: showing subscription usage (percent of limits) for a `claude -p` run

Ticket: https://github.com/NickSuomi/heron/issues/8
Researched 2026-09-29 against Claude Code docs at v2.1.285 (changelog: https://code.claude.com/docs/en/changelog).
V = verified in a primary source quoted or read this session. I = inferred.

## Verdict

Do not call `/api/oauth/usage`. If the feature is wanted, implement it behind an option, sourced from the `rate_limit_event` messages that `claude -p --output-format stream-json` already emits, and show it as a coarse hint, not a measurement. Details in section 4.

## 1. Is `/api/oauth/usage` documented or supported?

- V: No Anthropic page documents it. The docs' documented usage surfaces are `/usage`, the status line, and the Console/analytics pages (https://code.claude.com/docs/en/costs). The endpoint appears only in third-party and community issue threads (https://github.com/anthropics/claude-code/issues/31021, closed "not planned", no staff answer; https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202 calls it "undocumented"). The docs do say `/usage` fetches "your plan limits" from "the usage endpoint" and that it can be rate limited, with a 60-minute last-known fallback (https://code.claude.com/docs/en/costs, "When the usage request fails"); changelog 2.1.281 and 2.1.284 fix "repeated calls to the plan-usage endpoint" (https://code.claude.com/docs/en/changelog). So it is an internal endpoint of the client, not a contract.
- V: It is fragile in practice. Reported persistent HTTP 429 unless the request looks like Claude Code (User-Agent `claude-code/<version>`) (https://github.com/anthropics/claude-code/issues/31021, search summary of https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202). Anthropic is actively changing its client-side call pattern (changelog above). No stability promise exists.
- V: The token type matters. `claude setup-token` output (what `CLAUDE_CODE_OAUTH_TOKEN` holds) "can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors" (https://code.claude.com/docs/en/authentication#generate-a-long-lived-token). I: that scope statement suggests a setup-token token may not be entitled to the usage endpoint at all, or may lose access when Anthropic tightens scopes. The controller's successful call should be checked to have used exactly an operator's `setup-token` token, not a `/login` credential.
- Terms. V: OAuth authentication "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications". Developers building products should use API keys; Anthropic "does not permit third-party developers ... to route requests through Free, Pro, or Max plan credentials on behalf of their users", and developers "may not collect, store, or intermediate Claude.ai credentials or session tokens". It does not restrict "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription" (https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use). Also V: "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK" (same page).
- Is calling it permitted for an operator's own tool? I: No text permits or forbids it explicitly. The permitted path is the operator running the unmodified `claude` binary on their own token. A separate, hand-rolled HTTP client that presents that token to a non-public endpoint (and, to avoid 429, spoofs the Claude Code User-Agent) is outside "ordinary use of Claude Code" and is the pattern the terms warn about ("reserves the right to take measures ... without prior notice"). Risk is undefined, not proven. Anthropic's own guidance to ask is https://www.anthropic.com/contact-sales (linked from the legal page). Heron also would hold and use the operator's credential in its own code beyond spawning the binary; today it only passes it to `claude`.

## 2. Does Claude Code expose usage supportedly, readable from the `claude -p` run?

- V, best option: stream-json carries a rate-limit event. The Agent SDK documents `RateLimitEvent` "emitted when rate limit status changes (for example, from "allowed" to "allowed_warning")" with `rate_limit_info`: `status` (`allowed`/`allowed_warning`/`rejected`), `resets_at` (Unix seconds), `rate_limit_type` (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `overage`), `utilization` (float, "Fraction of the rate limit consumed (0.0 to 1.0)"), and `raw` ("Full raw dict from the CLI") (https://code.claude.com/docs/en/agent-sdk/python). The TypeScript reference lists `SDKRateLimitEvent` in `SDKMessage` (https://code.claude.com/docs/en/agent-sdk/typescript). The `claude -p` page says stream-json events are the same message stream (https://code.claude.com/docs/en/headless). I: the CLI writes these as `{"type":"rate_limit_event","rate_limit_info":{...}}` lines; confirm on the installed version with one real run (I did not run it: no token).
- Caveats, V: the event is emitted "when rate limit status changes", so a short run may emit none, or only when a threshold state changes; `utilization` and `resets_at` are optional (`None` allowed). I: it may show a window other than five-hour. Heron should treat "no event" as "unknown", not 0%.
- V: `result` message has `total_cost_usd`, `usage`, `modelUsage`, but the docs call cost a "client-side estimate" that "can differ from your actual bill" (https://code.claude.com/docs/en/headless#pipe-data-through-claude). On a subscription "the session cost figure isn't relevant for billing purposes" (https://code.claude.com/docs/en/costs). Tokens/dollars are not percent of plan; do not convert.
- V: Status line JSON has `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` (0-100) and `resets_at` (epoch seconds), present "only for claude.ai Pro and Max subscribers ... and only after the first API response", each window may be absent (https://code.claude.com/docs/en/statusline). It is the supported "percent" field. But it is produced by a `statusLine` command, which runs in the interactive UI; V that the docs describe it as a status bar run on events such as new assistant messages, and the `-p` page does not list it. I: it likely does not run under `-p`; unverified. Also V: `--bare` mode skips settings auto-discovery and OAuth credentials, so it cannot be combined with a subscription token (https://code.claude.com/docs/en/headless#start-faster-with-bare-mode).
- V: `/usage` shows plan bars, but "figures are approximate and computed from local session history on this machine" for the attribution part, and `-p` mode excludes terminal-UI-only commands (https://code.claude.com/docs/en/costs; https://code.claude.com/docs/en/headless "Command support differs in -p mode"). Not a programmatic route.
- V: OpenTelemetry export exists (https://code.claude.com/docs/en/monitoring-usage), but it reports tokens and cost, not plan percent. Not useful for this ticket.

## 3. Noise from other sessions

- V: All Claude surfaces share one limit: "your usage of all different Claude product surfaces (claude.ai, Claude Code, Claude Desktop) counts towards the same usage limit" (https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work). V: the weekly and five-hour windows are per account (https://code.claude.com/docs/en/costs, "Claude for Teams and Enterprise": rolling five-hour and weekly window, shared with chat and Cowork).
- I (arithmetic): granularity is 1% in the endpoint reading the controller saw; `rate_limit_event.utilization` is a float fraction (0.00-1.00) whose precision is not documented. A review run that is much smaller than 1% of a window will read as 0 or 1 whatever it cost, and any concurrent session, chat, or another Heron job on the same token adds unattributed points. Before/after difference is an upper bound on Heron's share only when nothing else ran, and cannot be certified. The window can also reset mid-run (`resets_at`), making a negative or wrapped delta.
- Also V: cache misses and long context raise plan usage in ways not visible in one run (https://code.claude.com/docs/en/costs, "Why usage climbs in a long session"), so percent per run is not stable for the same review.
- Suggested wording if shown: `Subscription usage after this run: five-hour window 27% (resets 14:00 UTC). Shared with all other sessions on this account; this is not this run's cost.` Show the level and reset time, not a delta. If a delta is shown at all: `about +2 points of the five-hour window (whole-percent resolution; other sessions may add noise)`, only when the reading is same window and non-negative; otherwise omit.

## 4. Recommendation

Do not implement the direct `/api/oauth/usage` call. Reasons: undocumented and unsupported (section 1), reported 429 behaviour, likely scope mismatch with a `setup-token` token, and it makes Heron a second client holding the operator's subscription credential outside the unmodified binary, which the terms treat as sensitive.

Implement, behind an off-by-default option, only the supported route: parse `rate_limit_event` from the existing stream-json output (no new credential use, no extra HTTP call, no extra usage). Show last observed `rate_limit_type`, `utilization` (as percent), `status` and `resets_at`, with the shared-account disclaimer, and print nothing when no event arrived. Do not compute per-run deltas in the default report. Keep `total_cost_usd` out of the percent line; if shown at all, label it an estimate.

Fallback if the event proves absent in real runs: do not show the feature, rather than fall back to the endpoint.

## Measured after the research (controller, 2026-09-29)

- A real `claude -p --output-format stream-json --verbose` run on a subscription account, with usage well below any limit, emitted one `rate_limit_event` with `{"status":"allowed","rate_limit_type":null,"utilization":null,"resets_at":null}`. So the supported route carries no percent in normal use; it can only say when a limit is near or reached.
- The controller's earlier call to `/api/oauth/usage` used an interactive-login credential, not a `claude setup-token` token, so open question 2 remains open for setup tokens.
