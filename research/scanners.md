# Scanner tools for Heron: licence, pinning, config-loading, tool shape

Question: https://github.com/NickSuomi/heron/issues/13. Date of research: 2026-09-30.
Legend: [V] verified against the cited primary source; [I] inferred, not tested.
Nothing was installed or run; every claim is from docs, source or registry metadata.

## How Heron runs helpers today (verified in the checkout)
- `rg` comes from `@vscode/ripgrep` 1.18.0 (ripgrep 15.0.0), resolved to its platform binary; run with `--no-config --hidden --no-ignore` (`src/harness/sourceTools.ts:13-22`, `:226`) [V].
- `ast_grep` comes from `@ast-grep/cli` 0.45.3, resolved to the native binary so its install script never runs; `pnpm-workspace.yaml` sets `allowBuilds: '@ast-grep/cli': false` and `minimumReleaseAge: 10080`. It is run with `--config=/dev/null` because the reviewed repo's `sgconfig.yml` `customLanguages` can load a native library (`sourceTools.ts:24-29`, `:254-266`) [V].
- Helpers run through `runTool` (`src/harness/tools/process.ts:30-47`): `spawn`, cwd = the checked-out tree, stdout fully kept, stdio ignored for stdin. Results are paged by `total`/`offset`/`next` (`sourceTools.ts:522`) [V].

## 1. gitleaks
- Licence: repo licence MIT, latest release v8.30.1 on 2026-03-21, repo pushed 2026-09-23, not archived. https://api.github.com/repos/gitleaks/gitleaks [V]. MIT permits an Apache-2.0 project to depend on and redistribute the binary if the MIT notice ships with it [I, standard MIT terms]. Default rules live in `config/gitleaks.toml` inside the same repo and are compiled into the binary: https://github.com/gitleaks/gitleaks/blob/master/config/gitleaks.toml [V per README, "default config built in to the binary"].
- Pinning: release assets are per-platform tarballs plus `gitleaks_8.30.1_checksums.txt` (e.g. `gitleaks_8.30.1_linux_x64.tar.gz`): https://api.github.com/repos/gitleaks/gitleaks/releases/latest [V]. The npm packages named `gitleaks` (1.0.0, 2022) and `semgrep` (0.0.1, 2022) are unrelated placeholders, do not use them (`npm view`, run 2026-09-30) [V]. So: fetch the tarball at image or package build time, verify a sha256 committed in the Heron repo, never at review time. `minimumReleaseAge` does not cover binaries; a 7-day age check has to be a manual or CI step [I]. Release cadence: 8.27.2 (2025-06), 8.28 (2025-07), 8.29 (2025-11), 8.30 (2025-11), 8.30.1 (2026-03): roughly 3-5 releases a year [V].
- Loads from scanned tree: README "Load Configuration" lists precedence: 1 `--config/-c`, 2 `GITLEAKS_CONFIG`, 3 `GITLEAKS_CONFIG_TOML`, 4 `.gitleaks.toml` in the target path: https://github.com/gitleaks/gitleaks/blob/master/README.md [V]. A `.gitleaks.toml` in the reviewed repo would therefore replace or extend the rules (and can allowlist secrets to hide them). Disable: always pass `--config <heron-owned file>` (wins over #4) [V by precedence; not run]. `.gitleaksignore` defaults to `.` (`-i/--gitleaks-ignore-path`) and `gitleaks:allow` comments are honoured unless `--ignore-gitleaks-allow`: point `-i` at an empty directory and pass `--ignore-gitleaks-allow` [V flags in README help]. Config is TOML regex and allowlists, not code [I]. Also keep `--max-decode-depth` and `--max-archive-depth` at their default 0 (no decoding, no archive traversal) [V] and do not use `--max-target-megabytes` (it skips big files; the owner forbids caps).
- Tool shape (proposal, invented names): `secret_scan { ref: source|target|base, paths?: string[] (subtree filter), offset?, limit? }` running `gitleaks dir --config <heron.toml> -i <empty dir> --ignore-gitleaks-allow --no-banner --redact --report-format json --report-path - <path>` (the `dir` command scans directories without git: README) [V flags; exact `--report-path -` stdout behaviour I]. Result: `{ total, offset, next, findings: [{ path, startLine, endLine, ruleId, description, fingerprint, redactedMatch }] }`. Use `--redact` so the secret never enters model context or an MR comment [V flag exists; verify in help before use]. Paged like `rg`. The description tells the model this is a candidate signal: it must open the file with the read tool and cite that line; a finding is never posted on the tool result alone.
- Runtime: no first-party benchmark for `dir` on ~5,000 files found. Third-party: Betterleaks' own numbers put Gitleaks at 24.5 s on the Rails git history and 11 m 28 s on the GitLab history, but those are git-history scans, not a single tree (https://appsecsanta.com/secret-scanning-tools/gitleaks-vs-trufflehog via search snippet, secondary) [I]. Estimate for one 5,000-file tree: seconds. Unmeasured; measure before shipping.

## 2. Semgrep Community Edition
- Engine licence: `semgrep/semgrep` LGPL-2.1, v1.178.0 on 2026-09-23, weekly-ish cadence (1.173 to 1.178 in six weeks): https://api.github.com/repos/semgrep/semgrep [V]. Running it as a separate process is compatible with an Apache-2.0 project [I, LGPL applies to the library, no linking here].
- Rule licence is the blocker. `semgrep/semgrep-rules` LICENSE is "Semgrep Rules License v1.0" (GitHub reports NOASSERTION): https://raw.githubusercontent.com/semgrep/semgrep-rules/develop/LICENSE [V]. The licence text says: use "only for your own internal business purposes", "does not allow you to distribute the rules, or to make them available to others as a service", licence is "non-sublicensable, non-transferable": https://semgrep.dev/legal/rules-license [V]. Consequence: Heron cannot vendor or ship the registry rules in an Apache-2.0 repository or image; each operator would fetch them himself, which breaks "no network during a review" unless the operator bakes them into a private image [I, not legal advice]. The Opengrep fork of the rules (`opengrep/opengrep-rules`) carries a Commons Clause ("right to Sell" excluded) on top of the fork: https://raw.githubusercontent.com/opengrep/opengrep-rules/main/LICENSE [V], so it is no cleaner.
- Pinning: PyPI wheels (manylinux/musllinux x86_64 and aarch64, cp310-cp314) and an sdist, no npm and no GitHub release binaries: https://pypi.org/pypi/semgrep/json [V]. Would need a Python runtime or pip-installed venv in the image; Heron is Node-only today.
- Loads from tree: with `--config <file>` rules come only from the given path; `SEMGREP_RULES` env also feeds `--config` (https://raw.githubusercontent.com/semgrep/semgrep/develop/cli/src/semgrep/commands/scan.py) [V]. Repo `.semgrepignore` is honoured for targeting (`--x-ignore-semgrepignore-files` exists, purpose undocumented in the source I read) [I]. Should run with `--metrics=off`, `--disable-version-check`, `--oss-only`, `--no-git-ignore`, `--novcs`, `--scan-unknown-extensions`, `--max-target-bytes` unset, and no `--config auto` (all flags present in scan.py) [V flags exist; behaviour I].
- Tool shape if ever added: `semgrep_scan { ref, paths?, ruleset: <Heron-named pack>, offset?, limit? }` returning `{ total, next, findings: [{ path, startLine, endLine, ruleId, message, severity }] }`.
- Runtime: no 5,000-file figure in primary sources. Semgrep says version 1.162 cut some P99 file-targeting times from about 60 min to under 12: https://semgrep.dev/blog/2026/making-semgrep-rip-how-ripgrep-inspired-us-to-shave-hours-off-some-scans/ (search snippet, not read in full) [I]. Runtime scales with rule count; expect tens of seconds to minutes [I].

## 3. ast-grep rule packs
- Licence: ast-grep MIT (https://api.github.com/repos/ast-grep/ast-grep, v0.45.3 2026-08-31, cadence about every 2-3 weeks) [V]; `@ast-grep/cli` MIT, single maintainer on npm (`herringtondarkholme`) [V via `npm view`]. There is no official, centrally licensed rule pack that I found; the docs catalogue is examples [I]. Third-party packs carry whatever licence their author chose [I]. Best fit: Heron writes and ships its own YAML rules under Apache-2.0 (no third-party licence question).
- Pinning: already solved (same dependency, `allowBuilds false`, `minimumReleaseAge`). Rules are files in the Heron repo, so no network [V for dependency; I for rules].
- Loads from tree: `sgconfig.yml` is read by default; `customLanguages.libraryPath` loads a tree-sitter dynamic library, i.e. native code from the repo (https://ast-grep.github.io/reference/sgconfig.html) [V]. Heron already blocks it with `--config=/dev/null` for `run`. For `scan`, the docs say `--rule <FILE>` runs a single rule "without project setup" and conflicts with `--config` (https://ast-grep.github.io/reference/cli/scan.html) [V]; whether `--rule` alone avoids reading the repo's `sgconfig.yml` needs a test [I]. Fallback: copy rules to a temp dir and use `--config <temp>/sgconfig.yml`, so the repo's file is never the config.
- Tool shape: `ast_rules { ref, pack: <Heron pack name>, rule?: <id filter (--filter)>, paths?, offset?, limit? }` with the same result shape as `ast_grep` plus `ruleId`, `message`, `severity`. It adds value only over today's `ast_grep` if the pack encodes non-obvious checks (for example `eval`, `innerHTML` and `v-html` sinks, `new RegExp($USER)`). Note `ast_grep` with an inline pattern already covers ad-hoc queries.
- Runtime: ast-grep is Rust and multi-threaded; I found no published 5,000-file figure [I]. Estimate seconds for a few rules [I].

## 4. osv-scanner (better-fit candidate for lockfile vulnerabilities)
- Licence: Apache-2.0 (same as Heron), v2.6.0 on 2026-09-14, cadence about monthly: https://api.github.com/repos/google/osv-scanner [V]. Redistribution allowed with NOTICE handling [I]. The vulnerability database (OSV) licence is separate; I did not verify it (OSV data is generally CC-BY 4.0, unchecked) [I].
- Pinning: release assets `osv-scanner_linux_amd64` (57.5 MB), `_arm64`, `osv-scanner_SHA256SUMS`, and `multiple.intoto.jsonl` provenance: https://api.github.com/repos/google/osv-scanner/releases/latest [V]. Not on npm (`npm view osv-scanner` 404) [V]. Offline: `osv-scanner --offline <dir>` uses a local DB at `$OSV_SCANNER_LOCAL_DB_CACHE_DIR/osv-scanner/npm/all.zip`, "will not download or update the local database, nor will it send any project or dependency information anywhere; no network connection is required": https://raw.githubusercontent.com/google/osv-scanner/main/docs/offline-mode.md [V]. The `--offline-vulnerabilities` variant may still call the network for transitive resolution, so use plain `--offline` [V]. Cost: the DB snapshot goes stale; Heron needs a scheduled refresh of `all.zip` (from `gs://osv-vulnerabilities`) baked into the image, with its checksum recorded [I].
- Loads from tree: `osv-scanner.toml` next to a lockfile applies (ignored vulns, package overrides, regex names; data only, no code): https://raw.githubusercontent.com/google/osv-scanner/main/docs/configuration.md [V]. Override with `--config=<heron empty toml>`, which "ignores osv-scanner.toml in all directories" [V]. `.gitignore` files are respected by default, so a repo could hide a lockfile [V, scan-source.md]; check the flags for turning that off before use [open].
- Lockfiles supported include `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`: https://raw.githubusercontent.com/google/osv-scanner/main/docs/supported_languages_and_lockfiles.md [V].
- Tool shape: `dependency_audit { ref, lockfile?: path (else auto-discover with -r), offset?, limit? }` running `osv-scanner scan source --offline --config <empty> --format json --lockfile <path>`; result `{ dbSnapshotDate, total, next, findings: [{ lockfile, package, version, ecosystem, advisoryIds, aliases, fixedVersion?, severity? }] }`. Include `dbSnapshotDate` so the model knows the age of the data. Evidence rule: a finding is cited only with the lockfile line the model read, and only when the MR adds or bumps that dependency; a pre-existing advisory is background, not an MR finding.
- Runtime: parsing lockfiles is cheap; no 5,000-file benchmark found, and file count barely matters because only lockfiles are read [I]. Recursive discovery over a large tree is documented as possibly slow (scan-source.md line 30) [V].

## 5. Other candidates seen
- Betterleaks (MIT, v1.9.0 on 2026-09-29, "maintained by the folks who made Gitleaks"): https://api.github.com/repos/betterleaks/betterleaks [V]. Its rules use Expr and can make HTTP validation calls (`-v/--validate`) https://raw.githubusercontent.com/betterleaks/betterleaks/main/README.md [V]. Both are risks if its config is ever read from the tree; young project, so it is a watch item, not a first pick [I].
- TruffleHog: AGPL-3.0, not suitable to bundle in an Apache-2.0 project [V licence via GitHub API; conclusion I]. detect-secrets: Apache-2.0 but last release 2024-05 [V].

## Recommendation
1. Add gitleaks first: MIT, one static binary with a published checksums file, all rules built in, tree-side config fully disabled by `--config` plus `-i` plus `--ignore-gitleaks-allow`, redacted output that fits the "candidate, cite the line" model. Lowest licence and integration risk.
2. Add osv-scanner second, after Heron decides how to ship and refresh the OSV DB snapshot. It is the only candidate that answers a question rg and ast-grep cannot (known-vulnerable versions) and is Apache-2.0.
3. Grow ast-grep with Heron-authored rules only if reviews show repeated missed sink patterns; no new dependency.
4. Do not add Semgrep: the rule licence bars redistribution, and the install is Python-only.
